# Mayday Landing 后续研究计划（2026-11-22 起）

当前功能见 [README](../README.md)，训练方法概要见 [训练概述](training-overview.md)。离线孪生里已经没有原生坠机，学习方法在加入阵风冲击后也追不上 prior，剩余差距主要来自观测延迟。所以下一阶段的重点不再是“训练更大的模型”，而是**用实机数据校准孪生、减少延迟造成的信息差、扩大可用场景**。每一项都写了通过门槛；没过门槛的结果不进正式版。

## 阶段 0：实机验收与数据回流（发布前后，持续）

- 按 [发布前清单](release-checklist.md) §1 完成 14 项实机场景。
- 小范围测试玩家的 F6 录制统一用 `probe_report.py` 汇总，建立一张“实机事件表”：接地下沉率、坡度、阵风冲击、HardLanding / Collision、交还原因。
- **门槛：** 至少 5 趟全自动落地没有否决项，才公开发布。

## 阶段 1：用实机录制校准孪生（最高优先级）

目的：确认孪生的失败分布和游戏一致，否则后面的训练都在优化错的东西。

1. **系统辨识：** 用录制里的操纵输入和运动响应，拟合俯仰 / 滚转响应、拉平时的升力、接地瞬间的下沉率。对比孪生的单步预测误差。
2. **阵风统计：** 实机已确认单次冲击为 ±12°；还需要统计阵风的**频率和时机**（离地多高时出现），与孪生的天气剖面对比。
3. **擦地复核：** 孪生预测大风天约 7% 擦地；用玩家的大风录制核对。差得多就先修孪生。
4. **门槛：** 孪生对实机录制的单步误差不超过当前水平；擦地率与实机在置信区间内一致。

## 阶段 2：减少延迟带来的信息差

剩余失败集中在延迟导致的“看到时已经晚了”。可尝试的方向，按成本从低到高：

1. **状态预测器：** 用已知的上一次操纵和观测年龄，把观测外推到“现在”，再交给 prior 和模型。先在 prior 上做，不需要重新训练。
2. **拉平前的坡度保护：** 离地较低时收紧坡度上限，提前修正侧滑（de-crab），直接针对翼尖擦地（坡度 > 9.06° 即判 Collision）。
3. **阵风后的快速恢复：** 检测到一帧内坡度突变 ≈ 12° 时，切到专门的恢复增益。阵风是游戏原生事件，冲击形状已知。
4. **学习方法只作为最后一步：** 只有前三项做完后，教师和 prior 之间仍有可观余量时，才再做 BPTT 或 DAgger。
- **门槛：** 在全新种子上，支持延迟段（0–300 ms）和阵风冲击场景都比 prior 提升，配对比较的置信区间不跨 0；任何场景不新增坠机或冲出跑道。

## 阶段 3：扩大可用场景

1. **巡航构型预位：** 孪生加入起落架收起、70 m/s 以上的起点，评估“预位 → 减速 → 截获”的全过程。必要时在面板上提示减速，而不是放宽窗口。
2. **单发与维修中进近：** 扩大单发分支的样本，单独统计成功率和交还率。
3. **双人联机（客户端驾驶）：** 用 `compare_traces` 对齐房主和客户端录制，测实际延迟分布；确认 0.3 s 交还规则是否合适。
4. **门槛：** 每个新场景单独报告成功率、交还率和坠机数；坠机数必须为 0 才允许在该场景接管，否则只给建议。

## 阶段 4：产品化

1. **英文界面：** 面板文字抽成字符串表，跟随游戏语言或用配置切换。N 网玩家多数需要英文（优先级可以提前到阶段 1 并行做，工作量小）。
2. **游戏更新防护：** 启动时检查 `CmdPilotAction` 编号、导航字段和 `UIF` / `PlaneStatusWidget` 是否存在，不一致就自动降级为 Advisor 并提示。
3. **模型晋级：** 阶段 2 有结果后，决定正式包内嵌哪个模型（`bptt-z2`、新模型或只用 prior），写进现状文档。
4. **玩家反馈通道：** 在面板上提示“遇到问题按 Shift+F6”，录制文件名带版本号和模型 SHA，方便对应。

## 不做或暂缓

- **继续扩大同类训练：** 已证明在阵风冲击下没有收益，除非阶段 1 发现孪生有系统性偏差。
- **强化学习：** 只在出现“教师在某场景系统性失败、且实机录制复现了这个失败”时再考虑。
- **起飞和航路自动化：** 不在本模组范围内（AutoFlight 另有负责）。

## 资源安排

- 大规模训练和评估使用云端 GPU；长任务要能断点续跑。
- 阶段 1 和阶段 2 的前三项主要是分析和规则修改，CPU 上就能完成。
